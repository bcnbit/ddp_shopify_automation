# RFC-0009 — Implementación

Conexión con Shopify por OAuth, con el access token cifrado en base de datos.

## El problema que corrige

La integración de RFC-0004 asumía una **aplicación personalizada con token pre-generado** en
el entorno (`SHOPIFY_ACCESS_TOKEN=shpat_…`). La aplicación real se ha creado en el
**Shopify Dev Dashboard** y su credencial empieza por `shpss_`.

`shpss_` **no es un Admin API access token**: es la **API secret key** de la aplicación.
Enviarla en `X-Shopify-Access-Token` no autoriza nada —la Admin API responde 401— y
además expone la credencial con la que se firman los intercambios OAuth. Los access token que
sí acepta la API empiezan por `shpat_`.

Se sustituye el token estático por un **flujo de instalación OAuth** que obtiene un *offline
access token*, lo guarda cifrado y lo entrega al transporte GraphQL como única fuente de
autenticación.

## Alcance entregado

- Tabla `shopify_installations` con el token cifrado (`encrypted`, `APP_KEY`),
  scopes concedidos, dominio y marcas de comprobación.
- Flujo OAuth completo: autorización, validación de `state` y `hmac`, canje y
  guardado.
- Pantalla **Configuración → Conexión con Shopify**, con estado, scopes, instalación y
  comprobación de sólo lectura.
- Comprobación de sólo lectura que confirma dominio `*.myshopify.com`, token, scopes y
  acceso a productos.
- Transporte GraphQL refactorizado: lee el token **sólo** de la instalación y rechaza cualquier
  credencial que no sea `shpat_`.

Queda **fuera** de esta fase, como pedía la petición: la publicación de productos, la
modificación de productos ya existentes en Shopify, los webhooks y el refresco de tokens
expirables.

## Decisiones técnicas

### El token deja el entorno y pasa a la base de datos

Un token en `.env` no se puede rotar sin desplegar, no se puede auditar y acaba copiado a
un `.env.example` por descuido. El token que produce un flujo OAuth pertenece a una
instalación concreta, así que se guarda con ella.

En el entorno quedan sólo las credenciales **de la aplicación**: `SHOPIFY_API_KEY`
(client ID, público) y `SHOPIFY_API_SECRET` (la `shpss_`, secreta). Está última se
usa para construir la URL de autorización y para verificar la firma del callback; **nunca** se
envía en la cabecera de acceso.

### El token se guarda cifrado con `APP_KEY`

El cast `encrypted` de Eloquent protege el token frente a una copia de la base de datos
(un *dump* de soporte, un backup en un bucket) sin protegerlo frente a la ejecución de código
en el servidor, que es la frontera realista. Se eligió frente a un KMS externo porque añadir un
proveedor de claves al MVP no cambia esa frontera, sólo la desplaza.

**Rotar `APP_KEY` invalida el token guardado** y obliga a reinstalar la aplicación. Es el
mismo efecto que ya tenía sobre el secreto TOTP de los administradores.

La prueba no se fía del cast declarado: lee **la fila cruda** con el Query Builder y comprueba
que el token no aparece en claro.

### La mutación es `productSet`, no `productCreate`

Sin cambios respecto a RFC-0004. Se repite aquí porque es la decisión que no debe revertirse sin
querer: `productCreate` sólo crea la primera variante y `productSet` es **destructiva
con los campos de lista**.

### `state` + `hmac`: el callback no puede depender de la sesión

El callback lo invoca una redirección del **navegador** de la persona que inició la instalación,
así que sí lleva su sesión; por eso las rutas viven dentro del grupo autenticado del panel y
heredan su autenticación y su segundo factor.

Pero la autenticidad **no** depende de la sesión, sino de dos comprobaciones que se hacen antes
de canjear el código:

1. El `state` devuelto coincide con el que se guardó en la sesión al iniciar. Se compara
   con `hash_equals` para no filtrar información por el tiempo de comparación.
2. La firma `hmac` es válida: se quita el propio `hmac` del conjunto, se ordenan los
   parámetros alfabéticamente como `k=v`, se unen con `&` y se calcula
   `HMAC-SHA256` en hexadecimal con la API secret key.

Sin la firma, cualquiera que conociera la URL de callback podría provocar una instalación. La
prueba que lo demuestra firma con **otra** secret: es una firma bien formada, y aun así se
rechaza.

El `state` se **consume** al usarlo (`session()->pull()`): un enlace de callback no
vale dos veces. Y se valida además que el `shop` coincida con `SHOPIFY_SHOP_DOMAIN`
si está definido, para que un enlace preparado para otra tienda no instale aquí.

### Tokens expirables: configurables, no expirables por defecto

La documentación exime a las **custom apps** de la exigencia de tokens expirables. La aplicación
es de una sola tienda, así que el valor por defecto es un token no expirable: sin
`refresh_token`, sin *job* de refresco y sin la ventana de fallo de 60 minutos.

`SHOPIFY_OAUTH_EXPIRING` permite pedir un token expirable, porque `expiring=1`
funciona en ambos tipos de aplicación mientras que `expiring=0` sólo en *custom*. **El
refresco no está implementado**: activar esa variable sin implementarlo deja la conexión rota en
una hora. Queda escrito en la RFC, en el `.env.example` y en la propia pantalla. Es deuda
explícita, no silenciosa.

### Una sola instalación

Reinstalar **reemplaza** la instalación anterior en lugar de acumular filas: la aplicación sirve
a una tienda. `ShopifyInstallation::current()` devuelve la activa.

### El prefijo se valida antes de llamar

`ShopifyGraphQlClient::usableTokenOf()` comprueba el prefijo y, si encuentra una
`shpss_`, lanza un error permanente que **nombra el problema**:

> `shpss_` es la API secret key de la aplicación, no un access token. […] instala la
> aplicación por OAuth para obtener un token `shpat_`.

Es la diferencia entre un 401 opaco de Shopify y un mensaje que explica el error real. La prueba
comprueba además que **no se ha enviado ninguna petición** con esa credencial.

### La comprobación de conexión es de sólo lectura, y una sola llamada

```graphql
query ConnectionCheck {
  shop { name myshopifyDomain }
  currentAppInstallation { accessScopes { handle } }
  products(first: 1) { nodes { id } }
}
```

Responde a las cuatro preguntas de la petición a la vez. Se mantiene en **una** llamada para que
no pueda degenerar en una batería de peticiones, y `products(first: 1)` basta para saber si
la lectura está permitida sin recorrer el catálogo.

El servicio **nunca lanza**: un fallo de conexión es un resultado que la pantalla muestra, no una
excepción que tumbe el panel. La prueba correspondiente lo verifica con un 401.

## Scopes

| Scope | Por qué |
|---|---|
| `read_products` | Leer productos para la idempotencia. |
| `write_products` | Crear el borrador. |
| `read_files` | Leer el estado de los medios subidos. |
| `write_files` | `stagedUploadsCreate` + `fileCreate` de la estrategia de imágenes. |

`read_files`/`write_files` **sí eran necesarios**: no son un extra especulativo, los
exige el código que ya existía en `ShopifyFileUploader` (RFC-0004). La prueba de la URL de
autorización fija la lista exacta y ordenada, de modo que añadir un scope de más rompe la suite.

## Pruebas

| Suite | Pruebas | Qué cubre |
|---|---|---|
| `ShopifyOAuthTest` | 18 | URL de autorización, `hmac`, `state`, dominio, canje y cifrado |
| `ShopifyOAuthCallbackTest` | 9 | El callback de extremo a extremo por HTTP |
| `ShopifyConnectionCheckTest` | 14 | Transporte: cabecera, prefijos y comprobación de sólo lectura |
| `ShopifyConnectionPageTest` | 13 | Pantalla, autorización y no filtración de secretos |

Las de la pantalla merecen una nota: una página de Filament es un componente Livewire, y todo lo
que sea propiedad pública **viaja al navegador**. Por eso la comprobación no se hace sobre la
intención del código, sino buscando literalmente el token y la secret en el **HTML renderizado**.
La página tampoco publica el modelo: pasa cadenas ya formateadas.

### Las pruebas se verificaron rompiendo el código a propósito

Un test que pasa **con el bug presente** no protege nada. Se rompió el código a mano y se
confirmó que las pruebas fallan:

| Se rompió | Resultado |
|---|---|
| Quitar la comparación del `state` | fallan «rechaza un estado manipulado» y «rechaza si la sesión no tiene estado» |
| Aceptar cualquier token sin validar el prefijo | falla «una instalación con `shpss_` no está configurada» |
| Guardar el token sin el cast `encrypted` | falla «el token se guarda cifrado y no en claro» |
| Publicar el modelo en la vista | falla «la pantalla no expone ningún secreto» |

## Puesta en marcha

1. Crear la aplicación en el **Shopify Dev Dashboard** y anotar client ID y API secret key.
2. Configurar la URL de redirección: `{APP_URL}/admin/shopify/callback`.
3. Rellenar el `.env` (nunca Git):

```env
SHOPIFY_API_KEY=...
SHOPIFY_API_SECRET=...
SHOPIFY_SHOP_DOMAIN=tu-tienda.myshopify.com
```

4. Entrar en el panel como administrador técnico y abrir **Configuración → Conexión con
   Shopify**.
5. Pulsar **Conectar con Shopify**, aceptar los permisos y volver. La pantalla comprueba la
   conexión automáticamente.

Desde consola, el diagnóstico equivalente:

```bash
php artisan shopify:check
```

## Pendientes y bloqueos

- **Refresco de tokens expirables.** No implementado (ver arriba). Necesario sólo si la
  aplicación se distribuye como pública.
- **Webhook `app/uninstalled`.** Si se desinstala desde Shopify, la fila local permanece y
  la pantalla seguirá diciendo que está conectada hasta que una comprobación falle.
- **Publicación.** Sigue fuera de alcance, como pedía la petición.
- **Ningún producto se ha enviado a una tienda real todavía**: no hay credenciales configuradas.
  La primera prueba contra una tienda de desarrollo es RFC-0006.
