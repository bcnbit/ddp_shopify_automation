# RFC-0004 — Implementación

Integración con Shopify e idempotencia. La ficha local es la fuente de verdad y
Shopify recibe **siempre** una copia en estado borrador.

## Alcance entregado

- Conector con la Admin GraphQL API, encapsulado tras `ShopifyProductGateway`.
- Envío como borrador con idempotencia en tres capas: no se duplica el producto
  remoto ni se vuelven a subir las imágenes.
- Subida de medios en dos pasos, conservando ALT, orden y foto principal.
- Registro de cada intento en `sync_attempts`, con causa legible y referencia de soporte.
- Reintento que **continúa** desde el punto donde quedó, no reinicia.
- Panel «Sincronizaciones con error» con botón de reintento autorizado.
- Dos comandos de consola para comprobar la conexión y enviar sin depender de la cola.

Queda **fuera** de esta fase la publicación: el MVP sólo sincroniza `DRAFT` y la acción de
publicar será un job separado (ver «Pendientes»).

## Decisiones técnicas

### Versión de la API

Se fija `2026-07`. La versión anterior del proyecto (`2025-01`) **está retirada**: Shopify
retira una versión cada trimestre y, ante una versión no soportada, responde con la más
antigua accesible, de modo que el contrato dejaría de ser predecible. La versión se lee de
`SHOPIFY_API_VERSION` para poder subirla sin tocar código.

> Cuidado al desplegar: una variable definida y **vacía** en `.env` anula el valor por
> defecto del código, no lo hereda. `SHOPIFY_API_VERSION=` dejaría la app sin versión.

### La mutación es `productSet`, no `productCreate`

`productSet` es la operación vigente recomendada: sustituye al conjunto `productCreate` +
`productUpdate` + `productVariantsBulkCreate`. Se eligió por dos motivos concretos:

1. `productCreate` **sólo crea la primera variante**; el resto exige llamadas aparte.
2. `productSet` admite `identifier`, que resuelve la idempotencia sin consulta previa.

**Aviso importante:** `productSet` es **destructiva** con los campos de lista. Hay que
reenviar *todas* las variantes y *todos* los medios en cada llamada, o Shopify elimina los
que falten. Cualquier cambio futuro que construya el payload de forma incremental romperá
esto de manera silenciosa.

### Medios en dos pasos

Los originales viven en un disco privado, así que Shopify no puede descargarlos por URL:
se reserva una URL temporal (`stagedUploadsCreate`), se suben los bytes y el resultado se
convierte en recurso (`fileCreate`) para asociarlo después con `productSet(files: …)`.

Dos detalles que costaron un fallo cada uno:

- El archivo debe subirse **el último** en el multipart: la firma de la URL temporal sólo
  es válida si el resto de campos la preceden.
- `duplicateResolutionMode: APPEND_UUID` es necesario para que el ALT se aplique.

### Estado siempre `DRAFT`

El estado se fija **dentro del gateway**, no se recibe de fuera. Un `ShopifyProductPayload`
con otro estado se rechaza antes de salir. Es lo que garantiza que ninguna ruta —presente o
futura— pueda publicar por accidente.

### Idempotencia en tres capas

1. Si la ficha conoce el GID, se **actualiza** ese producto (`identifier.id`).
2. Si no, se busca por el metafield privado `product_studio_id` y, como comprobación
   secundaria, por **handle**.
3. Un medio cuyo `sha256` ya tiene GID **no se vuelve a subir**.

El metafield se verifica **por cliente**. El filtrado por servidor sólo es fiable si el
metafield está declarado `adminFilterable`; si no lo está, Shopify ignora el filtro y
devuelve productos cualesquiera, y una ficha podría sobrescribir el borrador de otra.

### El reintento continúa, no reinicia

Un fallo deja el intento marcado y la ficha en `sync_failed`, con los GID que sí se
consiguieron ya persistidos. El reintento crea un **intento nuevo** (append-only) con la
misma clave de idempotencia y reutiliza lo ya hecho.

Un error **transitorio** (límite de llamadas, 5xx, timeout) se propaga para que la cola
aplique su backoff. Uno **definitivo** (token inválido, dato rechazado) no se propaga: no se
arregla reintentando.

### Autorización

La publicación exige `products.publish`, que **no** tiene ni la operadora ni el responsable;
sólo el administrador técnico. El botón se oculta además con la Policy, pero la decisión
real la toma la Policy: ocultar el botón no es la barrera.

## Pruebas

- `tests/Feature/Shopify/ShopifyGatewayTest.php` — **17 pruebas**. Contrato del conector con
  HTTP simulado: payload bien formado, ALT, token en cabecera, traducción de 401/429/5xx y
  de `userErrors`.
- `tests/Feature/Shopify/ProductSyncServiceTest.php` — **23 pruebas**. Orquestación con un
  gateway falso: cuántas veces se crea, con qué GID, qué pasa si un intento falla.

Dos niveles porque responden a preguntas distintas. El doble de HTTP no puede responder a
«¿dos clics crean dos productos?»: eso no es un problema de GraphQL sino de orquestación.

### Las pruebas se verificaron rompiendo el código a propósito

Un test que pasa **con el bug presente** no protege nada. Para evitarlo, se revirtió el
código a mano y se confirmó que las afirmaciones críticas fallan:

| Se rompió | Resultado |
|---|---|
| Pasar `null` en vez del GID conocido | falla «se actualiza en lugar de crear otra» |
| No persistir los GID de variante | falla «guarda los gid de las variantes por sku» |
| No marcar `SyncFailed` al fallar | falla «un error transitorio marca la ficha» |

Conviene repetir este ejercicio al añadir reglas de negocio nuevas.

### Criterios de aceptación del RFC

| Criterio | Prueba |
|---|---|
| Dos clics -> un único producto remoto | `test_dos_clics_seguidos_no_duplican_el_producto_remoto` |
| Modificar y actualizar el mismo producto | `test_una_ficha_ya_sincronizada_se_actualiza_en_lugar_de_crear_otra` |
| Error legible con referencia de soporte | `test_un_error_definitivo_no_se_propaga_y_deja_el_error_legible` |
| Reintento que continúa | `test_el_reintento_continua_desde_el_gid_ya_guardado` |
| Cero publicaciones accidentales | `test_nunca_envia_algo_que_no_sea_borrador` |

## Verificación manual

### 1. Comprobar la conexión

```bash
php artisan shopify:check
```

Sin credenciales responde con qué falta y dónde ponerlo; no intenta nada contra Shopify.
Con una instalación, valida token, permisos y versión de API con una consulta de sólo lectura.
La vía principal desde RFC-0009 es la pantalla «Conexión con Shopify»; este comando sigue
existiendo para soporte y para un despliegue sin navegador.

### 2. Configurar las credenciales

> **Enmendado por RFC-0009.** El token ya no se escribe en el entorno: la aplicación se
> instala por OAuth y el access token queda cifrado en base de datos.

```env
SHOPIFY_API_KEY=...        # client ID de la app (público)
SHOPIFY_API_SECRET=...     # API secret key (shpss_); SECRETA, nunca en Git
SHOPIFY_SHOP_DOMAIN=tu-tienda.myshopify.com
```

La **API secret key no es un access token** y no se envía en `X-Shopify-Access-Token`: esa
cabecera sólo acepta tokens `shpat_`, que entrega Shopify durante la instalación. Después de
rellenar el `.env`, se conecta la tienda desde el panel: **Configuración → Conexión con
Shopify**. La pantalla permite además comprobar la conexión con una consulta de sólo lectura.

### 3. Enviar una ficha

```bash
php artisan shopify:sync DDP-14666 --dry-run   # ver qué se enviaría
php artisan shopify:sync DDP-14666             # enviar de verdad
```

Al terminar imprime el GID, el handle y el enlace directo al borrador en el panel de Shopify.

### 4. Desde el panel

El botón «Enviar como borrador a Shopify» está en la ficha, y pasa a «Actualizar borrador»
cuando ya existe el producto remoto. **Encola** el trabajo, así que en local hace falta un
worker:

```bash
php artisan queue:work
```

Sin worker, el trabajo se queda en la tabla `jobs` y la ficha permanece en «Sincronizando».
Es la causa más habitual de que «no pase nada» al pulsar el botón en local. Para evitar
depender del worker, usar `shopify:sync`.

## Pendientes y bloqueos

- **Publicación.** Fuera del MVP por decisión del RFC. La Policy ya existe y exige permiso
  de Responsable; falta el job separado, con confirmación y comprobación de campos
  obligatorios. `ShopifyOperations` todavía **no** tiene la mutación de publicación
  (`productUpdate(status: ACTIVE)` o `publishablePublish`): habrá que verificarla contra la
  documentación vigente cuando se implemente, igual que se hizo con `productSet`.
- **Piloto real.** El flujo está verificado con dobles, pero **no se ha enviado nada a una
  tienda real todavía**: no hay credenciales configuradas. La primera prueba contra una
  tienda de desarrollo es RFC-0006.
- **Reordenado de imágenes.** La prueba cubre el servicio, no el gesto de arrastrar en el
  panel.
- **`sync_attempts` sin poda.** No hay política de retención; con el tiempo crecerá.
